# 基线与适配比较

## 基线最低要求

基线应：

- 与题目任务和评价目标一致；
- 能在当前数据/约束下运行或计算；
- 参数、假设和实现尽量少，结果可解释；
- 有明确输入、输出、失败边界和比较指标；
- 不因“简单”而被隐藏，也不因效果暂时较差而删除。

如果题目本质是约束优化，基线可以是可行规则/贪心/线性规划；如果是预测，基线可以是按时间或历史均值的朴素预测；如果是解释/估计，基线应与目标量和误差评价匹配。具体选择由团队确认。没有有意义的对照时，不要为了合同编造一条“最简单线性模型”。

## 适配矩阵

| 维度 | 要回答的问题 | 证据要求 |
|---|---|---|
| 题目映射 | 对象、任务、变量、约束和边界如何进入模型？ | question/anchor ID |
| 假设 | 哪些条件必须成立？题面/数据/团队依据是什么？ | assumption ID |
| 数据 | 需要什么样本、标签、时间和单位？现有数据能提供吗？ | data ID |
| 可解释 | 评阅者能否理解决策和失败边界？ | 变量/公式/图表 |
| 计算/实现 | 能否在竞赛时间和环境中运行？ | 代码入口/资源 |
| 验证 | 哪个实验能区分该模型与基线？ | validation ID |
| 复杂度 | 增加的复杂度换来什么可检验价值？ | 对照/消融/失败 |
| 表达 | 论文篇幅和读者能否承载？ | 章节/图表计划 |

## 常见误区

- “模型更复杂所以更好”；
- “指标提高所以题目适配”；
- “模型常见所以不能用”；
- “算法名称不同所以创新”；
- “代码能跑所以假设成立”；
- “不列失败方案就更完整”。

把这些句子改成需要证据回答的问题，而不是结论。

## 面向非专家的并列评估

候选模型至少用以下表格逐项呈现，不汇总为总分：

| 评估项 | 用户需要知道什么 | 结论格式 | 依据/未知 |
|---|---|---|---|
| 题目适配度 | 它是否直接处理本题的对象、目标和约束 | 较匹配/有条件/不匹配/未知 | question/anchor ID |
| 假设负担 | 需要用户接受哪些额外条件 | 低/中/高/未知 + 关键假设 | assumption ID |
| 数据准备度 | 现有数据是否包含所需变量、标签、规模和时间顺序 | 已具备/需补充/不确定 | data ID |
| 可解释性 | 团队能否说明输入如何影响输出、哪里会失败 | 高/中/低/未知 | 变量/公式/案例 |
| 计算与实现成本 | 在比赛时间和环境中能否实现、调试、复现 | 低/中/高/未知 | 资源/代码入口 |
| 验证准备度 | 是否已有能区分它与基线的实验 | 可验证/需设计/信息不足 | validation ID |
| 相比基线的潜在收益 | 可能多解决什么问题、是否值得付出代价 | 待验证描述，不写结果 | 对照假设/未知 |
| 失败边界 | 哪些输入、约束或数据质量下可能失效 | 具体情形/未知 | 边界或缺口 |

“较匹配”只表示当前输入下的适配判断，不表示更准确、更优或应当采用。每个“高/低”都要说明指标方向；成本和假设负担越低通常越容易承担，但这不是普遍优越性。

# MathModelingSkills

面向人机协作的数学建模工作台。

它帮你把一道赛题做成可复核的研究：读懂对象和机理，从文献与题目结构里长出模型，把计算跑清楚，再把论文写得像作者自己在说话。它不是代写系统，也不假装能替你决定该用什么模型。

人类拥有真正的建模判断——题意怎么理解、关键假设是否成立、模型是否采用、结果能否冻结、论文能否提交。Agent 负责理解、检索、推导、试算、解释、起草，以及那些本来就不该靠“记住去检查”的机械核验。

当前默认入口是 `math-modeling`。你先看到三个角色：建模手、编程手、论文手。后面二十多个 specialist 还在，只是普通对话不必先面对一整套流程节点。

> 当前版本是 **0.3.0-rc**。三角色入口和渐进加载已经落地；正在做语义收口和工具边界加固。真实 Agent 回放仍是发布门。CI 里的 pytest 只能说明契约没破，不能写成实践成功。

## 它在反对什么

数模里用 Agent，很容易滑向两种极端。

一种是把比赛做成流水线：先选题，再拆题，再选模型，再画规定数量的图，再按四段式写摘要。看起来完整，读起来却像同一套模板换了题目。另一种是把 Agent 做成算法目录：先判断这是优化题还是预测题，再从 NSGA-II、ARIMA、XGBoost 里挑一个“高级”方法。物理和工程题尤其吃亏——歧管微通道该怎么换热，并不因为标签里写了“优化”就该上多目标进化。

还有一种更隐蔽的失败：系统很擅长告诉 Agent **不要做错**，却没有足够的工具把该做对的事情做扎实。于是提示词越写越长，账本越积越多，用户说“继续问题三”，Agent 却先去检查 stage registry。

MMSkills 站在这两边之间。科学思考保持开放，机械执行尽量确定；角色只组织认知，skill 按需出现，而不是规定你必须按哪张图走路。

## 设计哲学

**问题先于方法。** 模型应该从对象、机理、约束、数据和要回答的问题里长出来，而不是从算法名称里选出来。领域知识承重的题目，先理解结构与过程，再读相关工作，再综合候选；抽象数据题不必为了“文献优先”去搜十篇无关论文。文献是证据，不是模板。论文用过某个方法，并不等于本题也该用。

**判断留给人，执行交给工具。** 越靠近科学判断，越少使用模板；越靠近机械正确性，越应该写成脚本。Agent 可以探索、比较、试算、起草，不必每一步都问“是否继续”。只有正式采用模型、冻结关键数字、提交终稿这类不可轻易撤回的动作，才需要人点头。解释雷诺数不必落盘；你说“全文统一叫 hydraulic diameter”，才更新术语表。

**差异来自题目，不来自换词。** 一篇像样的数模论文，靠的是这道题真正特殊的地方、团队真实做过的取舍，以及证据怎么组织。给普通事实起一个“多尺度协同响应机制”式的名字，或者为了显得独特强行上复杂模型，都不是我们要的原创。术语最好在分析阶段就定下来，写作阶段只检查有没有漂走——否则到终稿才统一用词，生造包装词已经写进正文了。

**论文要像人写的研究，不像流程报告。** 内部编号、阶段状态、待确认项属于追踪层；交出去的摘要、正文和图表属于成文层。自然化的验收标准是清楚、准确、符合作者意图，不是检测器分数，也不是固定章节或固定图数。一张调试残差图不必因为文件存在就进正文；一张承重的机理图，也不该因为“还没凑够八张”而被稀释。

**规则跟着赛事走。** CUMCM 的 AI 披露、页数和附录要求，不能自动变成 MCM 的规则。每条规则都要有赛事、年份、来源和核验日期；核过之前，宁可标未知，不要猜。

## 你怎么用它

多数时候，直接说你现在要做什么。

“先弄懂这个歧管结构”，走建模手，只加载题目熟悉。  
“根据这几篇文章讨论模型”，仍是建模手，打开文献与模型比较，不会顺便打开算法库。  
“跑一下问题三的敏感性”，交给编程手。  
“重写摘要”或“继续改 5.3”，交给论文手，直接改文本。

完整赛程初始化、跨会话恢复、提交前全检，才需要编排器。日常对话不预加载工作流，也不因为调用了某个 skill 就生成一份 ledger。

现有 specialist——题意、文献、假设、数据、实验、写作、图表、术语、审稿、自然化、TeX、披露、终检——都还在。它们是按需出现的能力，不是用户必须记住的菜单。

## 当前还缺什么

0.3.0 要把工程化放到该放的位置：引用核验、结果来源与过期、图文件质量、TeX/PDF 预检，能脚本化的就不要再写成“请记得检查”。这些工具只完成了一部分。

发布前必须有真实对话回放，而不是更多 fixture。至少要看到：局部请求不会启动全流程；物理工程题不会被算法名锚定；不需要文献时不会强行检索；建模阶段形成的术语在写作里能拦住包装词；代码重跑后旧数字会被发现。

## 仓库里有什么

```text
skills/       统一入口 math-modeling，以及按需加载的 specialist
docs/         架构、质量模型、决策记录与研究笔记
schemas/      跨技能共享的状态、证据、决策和实验契约
templates/    术语表、TeX 入口、披露与状态模板
profiles/     工作深度与赛事规则画像，不是第三套思维逻辑
tests/        契约测试和脱敏样本；真实回放另算
```

## Agent 安装

仓库地址：[`https://github.com/AlanAkillove/MMSkills`](https://github.com/AlanAkillove/MMSkills)

让 Agent 接入本项目前，先读[跨 Agent 安装教程与安装提示词](docs/agent-skill-installation.md)。不同宿主的 skill 目录、插件和项目指令并不通用；能 clone 仓库，不等于当前应用已经发现、启用或验证了这些技能。提示词可以直接复制：

```text
请将 https://github.com/AlanAkillove/MMSkills.git 接入当前 Agent；先判断你当前支持的 skill、插件或项目指令规范，再按教程选择适配方式并报告 copied、discovered、activated、verified 状态。不要把 Codex 的目录格式当成通用标准，也不要自动运行脚本或替我决定数学建模的核心内容。
```

## 使用与贡献

请先看 [CONTRIBUTING.md](CONTRIBUTING.md)。涉及竞赛规则、AI 使用或隐私的改动，需要同时留下来源、适用范围、人工确认点和脱敏测试；规则只有核验之后才能写进对应赛事 profile。

本地最小检查：

```text
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m compileall -q skills tests
```

TeX 模板另跑 `python skills/modeling-tex-paper-production/scripts/check_tex_template.py templates/tex/main.tex`；本机有 TeX 时再编译并看 PDF。

设计讨论可以继续读 [质量模型](docs/quality-model.md)、[实施路线](docs/implementation-roadmap.md)、[意图优先 ADR](docs/adr/0006-intent-first-adaptive-workflow.md) 和 [安装教程](docs/agent-skill-installation.md)。

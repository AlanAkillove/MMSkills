# ADR 0004：统一阶段注册表、跨审查 finding 与运行档位

## 状态

已接受（架构迭代）

## 背景

首轮实现把阶段依赖、审稿字段和过程产物分别写在编排脚本、多个 skill 和 Markdown 模板中。这样容易出现阶段命名漂移、同一问题被多个审查角色重复报告，以及完整流程在比赛时间预算下难以使用的问题。仅靠关键词/文件存在性测试也不足以证明 Agent 遵守了人工决策门。

## 决策

1. `schemas/stage-registry.json` 是默认阶段 ID、顺序、依赖和人工门的唯一来源；路由脚本读取它，不再内嵌第二份阶段图。
2. 审稿、主张—证据、术语、图表、阅读体验、AI 模板化和反同质化报告共享 `schemas/finding.schema.json` 的共同 envelope。各角色保留专属字段，但合并时按 `canonical_issue_key`、证据锚点和关系字段去重；冲突不得静默覆盖。
3. 提供 `research-full`、`contest-standard`、`contest-fast` 三个运行档位。档位只改变文档颗粒度和审查透镜选择，不能取消核心人工门、证据、失败记录、AI 使用事实或最终冻结。
4. 增加结构化行为回归场景，验证候选模型不被自动选定、全题目盘点不被省略、理解未确认不跳入模型，以及跨透镜 finding 不重复开单。
5. 保持通用架构与 CUMCM-first 规则实现的明确区分；其他赛事只能通过独立的、带来源和时效性的 profile 接入。

## 后果

新增或修改共享字段的成本提高，需要同步 schema、模板、skill、fixtures 和迁移说明；这是为了减少后期跨角色返工。行为回归默认验证结构化响应，不声称替代真实宿主 Agent 的模型级评估；宿主可将实际运行结果保存到 `tests/behavioral` 约定的 envelope 后复用同一验证器。

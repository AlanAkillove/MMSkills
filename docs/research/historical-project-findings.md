# 历史项目问题归纳（脱敏版）

本文件来自用户明确授权范围内的数学建模项目会话与其他历史项目会话的归纳，不保存原始对话、不公开具体论文内容，只提炼可迁移的问题模式。它是 skill 设计输入，不是对任何论文的最终评价。

## 1. 题意和对象语义

反复出现的问题不是数学公式本身，而是把示意图、结构关系或对象含义理解错。例如，曾出现过将不同层级的结构对象混同、由图形风格推断实体关系、没有先确认边界规则就开始建模的情况。

**设计要求**：`modeling-problem-intake` 必须先输出对象清单、关系图、边界条件、可疑歧义和待人确认问题；涉及图像/示意图时，必须把“图中直接可见”“题面文字明示”“模型推断”分开。

## 2. 术语膨胀与同义词漂移

历史修稿中反复发现：普通操作被包装成高承诺术语，同一概念在不同段落有多个名称，或为了避免重复而进行不必要的同义词替换。典型风险包括过度使用 `exact`、`certified`、`audit`、`law`、`semantics` 等词，以及把三个形容词堆在一个名词前。

**设计要求**：写前建立术语账本；每个新术语必须回答“是否需要命名、是否定义、是否至少多次承担功能、是否带来新的量/判据/操作”；全篇修改后做术语一致性扫描，普通事实优先恢复为标准表达。

## 3. 论文结构完整但像清单拼接

一些稿件章节齐全、语言顺滑、模型和实验都有，却缺少贯穿全文的“题目观察—模型决策—验证证据—结论边界”主线。后期只润色句子会让模板感更强。

**设计要求**：在写作前冻结问题地图、主张地图、证据矩阵和差异化账本；每一节说明它服务的主张和证据；如果一个段落不能回答本题的具体问题，应删除、合并或明确其作用。

## 4. 审稿中最容易暴露的实质问题

- 贡献表述比证据强，相关性写成因果性；
- 定理/命题的假设没有写在命题中，边界情况和空可行集没有处理；
- 算法没有伪代码或输入/输出/停止条件，代码和论文不一致；
- 只报告最好的结果，缺少基线、敏感性、误差或稳健性；
- 图表有数值但正文没有解释其与问题的关系；
- 数据切分或时间顺序不合理，存在泄漏风险；
- 为了显得先进选择复杂模型，模型与数据量/任务不匹配；
- 论文引用、代码、数据、支撑材料和最终 PDF 之间不能互相复核。

**设计要求**：审稿 skill 必须先事实核对和证据锚定，再写风格建议；重大问题以“为什么影响结论”和“如何验证修复”表达。

## 5. 读者体验和版式

反复修稿中，读者体验问题常常来自信息架构而非单句：结果先后顺序不自然、图表脱离叙事、段落过长、摘要与正文数字不一致、加入新解释后旧句没有删除、最终 PDF 出现空白页/标题孤立/图表拥挤等。

**设计要求**：设置独立的阅读体验审计和 PDF 视觉预检；先处理数字/主张/结构，再处理句式；每次插入内容后回读相邻句并检查冗余和分页变化。

## 6. 反同质化的来源

历史项目表明，同质化不是单纯语言问题：

- 不同题目使用同一套模型清单；
- 创新点只是把常见操作换成新名词；
- 图表类型和三点式结论固定不变；
- AI 生成的候选方案没有经过团队取舍，导致每篇文章都“合理但相同”；
- 论文去掉了失败尝试、边界和真正影响决策的观察。

**设计要求**：差异化从题意与模型阶段开始；保留真实取舍、失败边界和本题特有证据；不强行增加复杂模型，不输出原创度分数。

## 7. 人机协作过程

历史项目中较稳定的协作分工是：人类作为 `Research Chair` 负责方向和最终确认，Agent 分别承担资料侦察、模型候选、实验工程、对抗审稿、论文编辑和合规记录等角色。状态机和账本比“记住整段聊天”更可靠。

**设计要求**：采用 `INTAKE → RULES_PROFILE → QUESTION_MAP → BASELINE → MODEL_CANDIDATES → HUMAN_GATE → VALIDATION → PAPER → AUDIT → FREEZE` 的可回退流程，并将人类决定记录在 `decision_log.md`。

## 8. 该归纳不能推出的结论

- 不能据此判断任何具体论文是 AI 生成的；
- 不能把某一篇论文的术语偏好变成普适禁用词表；
- 不能把历史项目中的比赛规则复制到新赛事；
- 不能把“更自然”定义成更口语或更不规范；
- 不能把减少返工等同于让 Agent 自动完成核心建模。
